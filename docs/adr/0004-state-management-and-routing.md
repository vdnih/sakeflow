# ADR-0004: 状態管理・ルーティングは現状維持（StatefulWidget + setState / MaterialApp.routes）

> ステータス: Accepted
> 日付: 2026-08-15
> 決定者: プロジェクトオーナー + Claude Code

---

## 背景・問題

CLAUDE.md には初期整備時（2026-04-29, PR #3）から「状態管理: TODO（導入予定。Riverpod v2 推奨）」「ルーティング: MaterialApp.routes（GoRouter 移行検討中）」と書かれたまま、3ヶ月半以上決定されずに残っていた。実態は `StatefulWidget` + `setState`（6ファイル）、`Navigator.push` 系の直接呼び出し（12箇所）、`MaterialApp.routes` による2ルート（`/login`, `/home`）のみのフラットな構成で、Riverpod・go_router はいずれも `pubspec.yaml` に未導入。

「TODO」を書いたまま放置すると、次に触る人（未来の自分を含む）が毎回同じ判断を迫られ続ける。現状の規模（画面7つ、feature 7つ、ネストしたルーティングなし）では素の Flutter の機構で十分に足りており、決めずに残す理由がない。

## 決定

**現状の構成（`StatefulWidget` + `setState`、`MaterialApp.routes`）を正式な方針として採用する。** Riverpod・go_router の導入は「将来の TODO」から外し、具体的な痛み（複数画面をまたぐ状態共有が必要になる、ルートにパラメータ渡しやネストしたルーティングが必要になる等）が実際に発生した時点で改めて ADR を起票して判断する。

CLAUDE.md の「状態管理・ルーティングは未確定」という記述を削除し、確定した方針として記載する。

## 検討したが採らなかった案

- **今回 Riverpod + go_router へ移行する**: 採らなかった。現状の画面数・状態共有の複雑さでは移行コストに見合うメリットが無い。中断していたプロジェクトの再開直後に大規模な基盤変更を行うのはリスクが高い。
- **「検討中」のまま残す**: 採らなかった。3ヶ月半決まらなかった実績があり、決めずに残すこと自体が次回再開時のコストになる。

## 影響範囲

- `CLAUDE.md` の「3. アーキテクチャ」節の記述を「未確定」から「確定」に変更。
- 新規実装時にコード上の判断基準ができる: 画面ローカルな状態は `setState`、画面間の単純な遷移は `Navigator.push` でよい。状態管理ライブラリの導入は本 ADR を覆す新しい ADR が無い限り行わない。
